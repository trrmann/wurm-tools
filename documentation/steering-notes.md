## Requirement-to-implementation register

**Current signing clarification (2026-10-25):** The user has only one Fedora laptop,
which will remain internet-connected, no known hardware token, and no security-admin
expertise. The earlier hardware-only assumption is superseded for this workflow.
The [plain-language guide](helper-signing.md#start-here-one-fedora-laptop-no-security-expertise-required)
and explicit `setup-local` / `sign-local` actions support password-protected local keys.
`USE THIS LAPTOP` consent is required locally before creating the identity; hardware
commands retain their original checks. No real identity/signatures or recovery proof
have been created by implementing this alternative.

**Timeout recovery:** `helper:signing:setup recover-local` now preserves a partially
created local identity and completes only missing key/certificate steps with explicit
consent. `sign-local` verifies/preserves existing valid signatures and fills missing
ones across both profiles; wrong-key/invalid signatures and stale sources still block.
No password reset, secret export or identity replacement is performed by recovery.

## Release completion checklist

**Automatic source/installer gate:** Production deployment now runs
`check-helper-installers.js --rebuild` before Git operations (and again after a source-changing
rebase). It rebuilds and tests both Fedora profiles. Packaging fingerprints source/config/tests/docs
and rejects drift; acceptance rejects stale/missing provenance and changed artifact hashes.
Use `pnpm run helper:installer:refresh` manually to rebuild/test and
`pnpm run helper:installer:check` to check freshness. The gate requires the Fedora x64 release
host and its build prerequisites; Windows production deployment cannot bypass it.
Freshness does not grant signing or public-release approval.

**Signing assistance:** Run `pnpm run helper:signing:setup --help` and follow
[the one-laptop beginner workflow](helper-signing.md#start-here-one-fedora-laptop-no-security-expertise-required).
Generating a new identity is explicitly confirmed, never a side effect of install/build/tests.
The optional hardware workflow uses an offline primary. The local alternative
instead requires explicit approval to keep keys on this laptop; it does not require
disconnection. Hardware signing still accepts only the matching token's signing
subkey with the primary secret absent. Script tests are
not evidence of physical token provisioning, recovery readiness or real signatures.

- [ ] Both rebuilt profiles pass freshness and their applicable acceptance on the final source.
- [ ] Real Fedora KDE desktop login/start/stop/update/recovery is verified (not a systemctl/editor fixture).
- [ ] Protected signing identity is provisioned, publisher trust distributed and signed artifacts verified.
- [ ] Redistribution licenses/notices and support/maintenance ownership are approved.
- [ ] Windows 10/11 discovery, implementation and separate native acceptance pass.
- [ ] Publish versioned approved downloads and wire the website's OS-aware install/update handoff.
- [ ] Verify the published installers and website end-to-end; only then close the parent installer task.

There is no claim that the checklist is complete. Real signing/recovery, Windows execution
and real desktop login cannot be substituted with Linux unit tests or unsigned container builds.
